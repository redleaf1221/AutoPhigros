# 判定机制：四类音符与噪域

这份文档讲**游戏怎么判**：先给一份能直接用的 TL;DR，再把容差、窗口、挑音符的顺序这些底层
细节摊开。所有数字都来自 [Phigros4.0-音游内核逆向报告.md](Phigros4.0-音游内核逆向报告.md)
（每条都标了函数地址与章节），代码里的唯一实现是
[algorithms/judging.py](../src/algorithms/judging.py) —— 自检、`judge.py`、规划器都从它读，
不许各写一份。

**单位**：几何坐标在**虚拟屏**上（官谱 16×9）。游戏的容差写作**谱面单位**（Tap 1.9 / Drag 2.1），
乘 `CHART_TO_SCREEN = 0.9` 得虚拟屏单位（1.71 / 1.89）。下文凡是谱面单位都会注明。

---

# 一、TL;DR

## 1. 每帧发生什么

```
每一帧（60fps 量级）：
  1) CheckBlocks()        —— 4.0.1 起：把踩进噪域的手指从 fingers 里摘掉（先于判音符！）
  2) GetFingerPosition()  —— 给每根手指、每条判定线算"横向偏差"
  3) 逐个手指：按下了？   → CheckNote()   挑一个 Tap / Hold 头判掉
              新起手？   → CheckFlick()  点亮一个 Flick
  4) 逐帧驱动各控件：Drag / Hold 身体 / Flick 自己再判一遍（不看有没有新按下）
```

关键：**判定线是无限细的一条线**。`GetFingerPosition` 会算"横向"和"法向"两个量，但只有
**横向**进门槛 —— 手指离判定线多远都无所谓，`CheckNote` / `CheckFlick` 从头到尾没读过法向
那一个。这就是"垂直判定"。

## 2. 四类音符

| 类型 | 怎么算过 | 结算成什么 |
|---|---|---|
| **Tap** | 需要一次**按下**：那一刻在扫描窗内、横向够得着（< 1.9 谱面单位） | Perfect / Good / Bad；没人按 → Miss |
| **Hold** | 头判和 Tap 一样（但要**留住手指**）；按住期间每帧只要有**任一**按着的手指横向够得着就续命 | Perfect / Good / Miss（**没有 Bad**），分数在**尾部**结算、报的是**头判**的档 |
| **Drag** | **不需要按下**：任意时刻在 `±0.1s` 内有**任一按着的手指**横向 ≤ 2.1（比 Tap 宽） | Perfect / Miss |
| **Flick** | 需要一次**"新起手"**：手指瞬时位移够大（游戏按速度算，我们按跳变认）；光摆在那儿不算 | Perfect / Miss |

再补四条容易踩的：

* **一次按下只判一个音符**（先到先得）。Tap 一次按下判一个 Tap 或 Hold 头；这一次按下**还能顺手**
  把某一个 Drag 标掉、或把某一个 Flick 点亮（那是另外两条判据，不占"这一个"）。
* **Bad 只可能出现在"早"的一侧**：晚的限制是 +0.18s，而 Bad 的门槛是 |Δ| ≥ 0.18 —— 晚到那儿
  早就判不到了。所以"手感差"只会表现成按早了。
* **蹭键（graze）**：按下落在游戏的扫描窗里、却不在"这一下是为它按的"那个窄窗
  （`HEAD_WINDOW = (−0.02, +0.16)s`）里 —— 音符被它判掉了，但不是为它按的。规划器把这算成失误。
* **噪域吃掉的手指不判音符**：那根手指在"踩进去 → 抬起"这一段里等于不存在（见 §5）。

## 3. 分数

`分数 = 900000 × acc + 100000 × maxCombo / N`，`acc = (Perfect + 0.65 × Good) / N`。
Bad 与 Miss 在 `acc` 里都是 0 分（Bad 只是不断连击，Miss 断连击）。

## 4. 窗口速查

| 项目 | 值 | 严格性 |
|---|---|---|
| 判定扫描窗（Tap / Hold 头） | 早 **0.22s** / 晚 **0.18s**（不对称） | 两端都**严格**（`<` / `>`） |
| Tap 档位 | `\|Δ\| < 0.08` Perfect，`< 0.18` Good，否则 Bad | 严格 |
| Tap Miss 线 | 音符时刻 **+0.18s** | —— |
| Hold 结算 | `时刻 + hold − 0.22s`（手指可以**早走 220ms**） | —— |
| Hold 身体容忍 | 连续 **3 帧**都够不着才 Miss（`_safeFrame = 2`） | —— |
| Drag | `\|Δ\| ≤ 0.10s`，横向 **≤ 2.1**（谱面单位） | 窗口与容差都是 `<=` |
| Flick | `\|Δ\| < 0.14s`，横向 **< 2.1**，且需要新起手 | 窗口与容差都是 `<` |
| Tap / Hold 横向 | **< 1.9**（谱面单位）＝ 1.71 虚拟屏 | `>=` 即跳过 |
| 横向"边缘收窄"起点 | **0.9**（谱面单位） | 只收紧**早**的那一侧 |

## 5. 噪域（4.0.1 新增）

一句话：**触点落进生效中的噪域，那根手指当帧就被游戏从 `fingers` 里摘掉，而且废到抬起来为止**
—— 中途挪出去也不算数。所以对规划来说它是一块"踩进去就永久损失一根手指"的禁区。

* **不影响分数与连击**：`FreezeScore` / `BlockCombo` 只冻 UI（藏分数、藏连击）。
* **判定先于音符**：`CheckBlocks()` 在 `CheckNote` 之前跑，所以"当帧踩进去"和"当帧判音符"是
  互斥的 —— 手指先没了，那个音符就判不到。
* **躲法**：沿判定线的**法向**平移不改变横向偏差 → 不损失判定。这是规划器最主要的躲避手段。
* **它有生命周期**：`[appear, disappear)` 决定画不画、`[enable, disable)` 决定吃不吃人
  （两个窗口可以不一样）；窗口内还会按 scale → rotate → move 三组键帧动来动去。

底层细节见第二部分 §7；工程上"机制一份、策略四份"的分工见 [impl.md](impl.md#机制一份策略四份2026-10-14-拆开)。

# 二、底层细节

## 0. 坐标与单位

* 谱面里 `positionX` 是**沿判定线的横向偏移**（世界单位），乘 `NOTE_X_SCALE = 0.9` 得虚拟屏单位；
  `time` 的单位是 1/32 拍（`tick × 1.875 / bpm` 秒）。
* 判定线在任意时刻的位置与朝向由 move / rotate 事件**分段线性插值**得到
  （`JudgeLineControl::UpdateInfo` 把 `(raw − 0.5) × 10` 与角度原样写进 transform，不取反不翻转）。
* 判定用的横向偏差：`(手指 − 判定线原点) · 判定线朝向 − note.offset`，取绝对值。
  手指与判定线必须**同刻**取——判定线一直在动，所以这个量是逐帧漂的。
* 音符的"落点"（音符在屏幕上离判定线多远、往下掉到哪）**与判定无关**，只影响观感。

## 1. 每帧的顺序（`JudgeControl::Update` `0x1d207e4` / `0x1d71d20`）

```c
if (previewElementUpdateControl->_HasBlocks) CheckBlocks();   // 0x1d72100，4.0.1
GetFingerPosition();                                          // 所有手指都算，不看 phase
foreach (finger) {
    if (finger.pressed)              CheckNote(fingerIndex);   // 0x1d21104
    if (finger.isNewFlick /*LOBYTE*/) CheckFlick(fingerIndex);  // 0x1d21828
}
```

`CheckNote`（Tap 与 Hold 头判）**只在"按下事件被处理的那一帧"跑一次**；Drag / Flick / Hold 身体
不吃这一条，它们逐帧读位置：

```c
foreach (clickControl) if (note->realTime <= nowTime + 2.0) ClickControl::Judge();
foreach (dragControl)  { DragControl::NoteMove();  DragControl::Judge();  }
foreach (holdControl)  { HoldControl::NoteMove();  HoldControl::Judge();  }
foreach (flickControl) { FlickControl::NoteMove(); FlickControl::Judge(); }
```

## 2. 扫描窗与三档窗口

三档窗口是 `JudgeControl` 的静态字段，**别的判定也读它们**：`PerfectTimeRange = 0.08`、
`GoodTimeRange = 0.18`、`BadTimeRange = 0.22`。

`CheckNote` 每帧只看 `realTime ∈ (nowTime − 0.18, nowTime + 0.22)` 的音符：下界取 `GoodTimeRange`、
上界取 `BadTimeRange`，两端都严格。反过来看**早晚量** `Δ = nowTime − realTime`：

```
Δ ∈ ( −0.22 , +0.18 )      早 220ms、晚 180ms，不对称
```

Flick 的候选窗是另一套：`PerfectTimeRange × 1.75 = 0.14`，即 `±0.14s`，两端也严格。

## 3. 横向容差与"边缘收窄"

`CheckNote` 第 186–213 行：

```c
if (touchPos >= 1.9) goto skip;                       // 硬阈值，>= 就跳过（谱面单位）
badTime = 0.22;
if (touchPos > 0.9)
    badTime += (touchPos - 0.9) * 0.08 * (-0.5);      // 越小越窄，touchPos = 1.9 时收到 0.18
if (delta < -badTime) goto skip;                       // 只收紧**早**的那一侧
```

也就是说：横向偏得越多，**早**的那一侧能容忍的提前量越小（1.9 处正好收到 0.18，Bad 那一档
消失），而**晚**的那一侧固定由扫描窗（+0.18）管。Tap / Hold 头判的横向容差就是这条 1.9
（Tap 与 Hold 共用 `CheckNote`）；Drag / Flick 各走各的 2.1。

`GetFingerPosition`（`0x1d20d10` / `0x1d212b4`，两个重载）为每根手指、每条判定线算出横向与
法向两个量，`CheckNote` **只取横向那一个**。法向分量不进任何门槛，只在"多个候选挑一个"的
度量里出现（权重 `1/2.2`，见下）。

## 4. 一次按下怎么挑音符

`CheckNote` 的挑法比"取度量最小"绕得多，四类音符都进候选（Flick 只挑不判）：

1. 每个候选过三道门：已判过 / 横向 `>= 1.9` / 早侧收窄的 `badTime`；
2. 还没有 best 就**直接接受**；
3. best 是 Drag / Flick → 下一个过门的候选**无条件**顶掉它；
4. best 是 Tap / Hold → 候选也得是 Tap / Hold、且两者 `realTime` 差 **≤ 10ms**，才比度量
   （度量**严格**更小才顶替；差在 `0.005` 虚拟屏单位以内算平局，保留先遇到的）；
5. 每次接受候选都会把 `minDeltaTime` 记成那个候选的 `|realTime − nowTime|`，往后
   `realTime − nowTime >= minDeltaTime + 0.01` 的候选**看都不看** —— 这才是"一次按下够不到太远的
   音符"的真正原因（函数开头把 `minDeltaTime` 写成 `10000.0f`，只为让第一个过门的候选无条件通过）。

挑用的度量是

```
metric = |Δx| + |Δy| / 2.2
```

`|Δx|` 是横向偏差、`|Δy|` 是到判定线的法向距离 —— 法向在这里才有存在感。

## 5. 四类音符的完整规则

### Tap —— `ClickControl::Judge` `0x1d3060c`

* 由**一次按下**判：过 §4 的三道门 + 拿到 best → 按 `|Δ|` 分档（0.08 / 0.18）；
* 一次按下只判一个，判过就标 `judged`；
* 没被任何按下选中 → 在 `音符时刻 + 0.18s` 判 Miss（读的还是 `GoodTimeRange`）。

### Hold —— `HoldControl::Judge` `0x1d32668`

* **头判**：同 Tap（一次按下、1.9 横向、`badTime`）。头判当场**不算分**，只记下
  `_judgeTime`（＝头判的 Δ）与 `isPerfect`；`|Δ| >= 0.18` 时游戏会把标记清掉继续等，
  下一次按下还能判它。
* **身体**：只在头判之后跑，逐帧查**所有按着的手指**（不看 `phase`），横向 < 1.9 就刷新
  `_safeFrame = 2`；连续 **3 帧**（`if (--_safeFrame < 0)`）都够不着 → 当场 Miss。
* **收尾**：在 `realTime + holdTime − 0.22` 结算，**报头判的 Δ 与档**（Perfect 或 Good），
  所以 Hold **不会**出 Bad。
* 头判从没成功 → 在 `音符时刻 + 0.18s` 判 Miss（读的是 `GoodTimeRange`，不是 0.22）。

### Drag —— `DragControl::Judge` `0x1d313f0`

* **不需要按下**：`|Δ| <= 0.10s` 的窗口内逐帧比位置，只要有**任一按着的手指**
  横向 `<= 2.1`（比 Tap 宽）就算够到 → Perfect；
* 不看 `phase`（读的是每帧的 `fingerPositionX` 数组）；
* 窗口过完都没够到 → Miss。

### Flick —— `CheckFlick` `0x1d21828` + `FlickControl::Judge` `0x1d319e4`

* **光摆在那儿不算**：要一次"新起手"（`Fingers.isNewFlick`）。`FingerManagement::Update` 按瞬时
  速度算（`|nowMove| / deltaTime` 超过 `flickJudgeSpeed × 5`），阈值随 dpi 归一、拿不到，
  所以重放里只认**位置跳变**（≥ 1 虚拟屏单位）—— 跳变才一定够快，报问题才值得看一眼。
  手指从抬起的旧位置"出现在"新位置也算一次起手（同样是悲观的那一侧）。
* `CheckFlick` 把候选收窄到 `type == 4`、窗口 `±0.14s`、横向 `< 2.1`，挑法与 `CheckNote` 同源；
  每次起手只点亮一个，点完清 `isNewFlick`。
* 被点亮 → Perfect（`at` 取点亮那一刻）；迟到 `−0.14s` 之外 → Miss。**没有 Good / Bad。**

## 6. 手指模型与音符身份

我们把一份规划重放成"手指时间轴"（`Fingers`）：把事件按指针拆开，任意时刻取每根手指**上一次
事件**的位置，只要那一次不是 UP 就算还按着。手指在两次事件之间不动，判定线却在动，所以横向
偏差是**逐帧漂**的 —— 这也是"一次按下判完就走、别赖着不动"的原因之一。

音符身份（设备日志逐音符对账用，`SetCodeForNote`）：

```
noteCode = 线号 × 1000000 + (线上面 = 0 / 线下面 = 100000) + 该侧第几个 × 10
```

上面/下面各算各的序号（`slot.side_index`）。`judge.py --compare` 就是拿它把每条判定与设备
日志里的那条对上。

## 7. 噪域：数据 → 几何 → 判定

### 7.1 数据（`GameInformation.BlockArea`，size 0x50）

```
topRightPercentage / bottomLeftPercentage   两个百分比角（0~1，x 右 y 上）
appearTime / enableTime / disableTime / disappearTime
isSubtract                                  洞（见 7.3）
moveEvents / scaleEvents / rotateEvents     三组键帧（每组的字段见报告 §2.6）
```

* `[appear, disappear)` 决定**画不画**（窗口外游戏把位置甩到 x=1000）；`[enable, disable)`
  决定**吃不吃人**。两者可以不一样。
* `blockAreaList` 是 4.0.0 就有的字段，但 4.0.0 的谱面**一张都没用过**；4.0.1 才真正启用。

### 7.2 几何

* 百分比 → 世界：`(p − 0.5) ⊙ (screenWidth, screenHeight)`，`p.y = 1` 在**上**边（与音符同一个
  空间，`UpdateBlocksTransform` `0x1cdb5b0` / `GetBlockGeometry` `0x1cdbb38` / `AnchorToWorld`）。
* 块的尺寸 = `|Δp| ⊙ (screenWidth, screenHeight)`（单位方块 × `lossyScale`）。
* 键帧按 `UpdateBlocksTransform` → `UpdateBlockAnimations` 的顺序叠：**scale → rotate → move**，
  每个事件带自己的锚点，锚点会把块心一起挪；缓动是 15 张 101 点的表
  （`GetEase::Instantiation` `0x1cc95e4`，`GetEaseWithProgress` `0x1cc92fc` 查表 + 线性插值），
  `SafeDiv`（`0x1cdc518`）除零时返回 **1.0**。
* **镜像**（`GameInformation::BlockArea::Mirror` `0x1cbe3e4`）只翻 x：两个角的 x 互换并取
  `1 − x`、rotate 的锚点 x 翻且角度取反、move 的终点 x 翻、scale **只翻锚点 x**（倍率不动）。
  谱面镜像时 `blockAreaList` 跟着翻。

### 7.3 判定：两块矩形 + 两道奇偶门

`TryGetBlockingBlock`（`0x1d735d8`）对每块**生效中**的块算两个矩形：

* **原矩形**（`IsPositionInsideOriginalBlock` `0x1d73b80`）：逆变换后 `|x| ≤ 0.5 && |y| ≤ 0.5`；
* **inset 矩形**（`IsPositionInsideBlock` `0x1d73c7c` + `TryGetBlockTouchHalfSize` `0x1d73d08`）：

```
v = 0.05 × 屏高                                  # 世界单位（blockTouchInsetScreenHeightRatio = 0.05）
half.x = 0.5 ± min(v / |lossyScale.x|, 0.25)     # 局部单位（maxBlockTouchInsetLocal = 0.25）
half.y = 0.5 ± min(v / |lossyScale.y|, 0.25)     # isSubtract 为真取 +（往外扩），否则取 −（往里收）
```

两个常量都出自构造函数 `JudgeControl::JudgeControl`（`0x1d73e88`）里那一句 8 字节写
`*(_QWORD *)&this->blockTouchInsetScreenHeightRatio = 0x3E8000003D4CCCCDLL`
（低 32 位 0.05、高 32 位 0.25；两字段相邻，编译器合并成一次写，所以第二个字段没有自己的赋值语句）。
`lossyScale` 是块**当前**的世界尺寸（键帧缩放之后），不是基础矩形。

然后两道门（`v23` 是原矩形命中且 subtract 的块数，`v24` 是"原矩形命中了某个非 subtract 块"，
`v22` 是 inset 矩形命中且 subtract 的块数，`v25` / `v53` 是第一个命中的非 subtract / subtract 块）：

```
if ((v24 ^ v23) & 1) == 0                       → 不吃      # 第一道：必须命中某个**原矩形**
if ((v22 & 1) == (v25 != null ? 1 : 0))         → 不吃      # 第二道：inset 矩形的奇偶
否则返回 v25 ?? v53                                        # 是哪个块吃的不影响结果
```

它看着像"奇偶填充"，但两套矩形各算各的：**原矩形管第一道门、inset 矩形管第二道门**。
推论（我们拿来证明"保守禁区不会漏"）：第一道门要求点落在某个块的**原矩形**里，所以
**真命中集 ⊆ 所有活跃块原矩形的并集**，与 inset 无关。

**吃到会怎样**：`CheckBlocks`（`0x1d72100`）把命中块的触点 id 塞进 `blockedFingerIds`，
再把 `fingers` 里 id 在其中的**整条删掉**（不是判 Bad，是这只手当帧起不存在）；`blockedFingerIds`
只在**手指抬起**时清（`SyncFingers` 的 `RemoveWhere` 判据是"这个 id 已经不在当前 touches 里"）。
于是：**踩进去 → 废到抬起，中途挪出去也不算数**。

副作用：`UpdateLowPassFilterState`（`0x1d7332c`）会切低通滤波并抛 `TouchBlockStateChanged`；
`FreezeScore` / `BlockCombo`（`0x1d87d80` / `0x1d87e9c`）只动 UI。

## 8. 我们这套重放里的已知近似

重放不是模拟器，下面这些是**明写的假设**，出问题时先看这里：

| 假设 | 值 / 做法 | 为什么 |
|---|---|---|
| 送达到判定的延迟 | `PROCESS_DELAY = 0.029s`（实测中位 +28.9ms，分布 12~48ms） | 触摸由游戏在之后某一帧处理；播放器按 latency 提前发，正好抵掉 |
| 帧率 | 60fps | Drag / Hold 身体 / Flick 要逐帧采样；真机可能是 60 或 2×刷新率，帧相位不可知 |
| Flick 的"够快" | 位置跳变 ≥ 1 虚拟屏单位（`FLICK_JUMP`） | 游戏按瞬时速度、阈值随 dpi 归一，拿不到；跳变是**悲观**的那一侧 |
| 距离比较 | 差在 `0.005` 虚拟屏单位以内算平局 | 游戏比的是活 transform 的两个 float，我们用插值出的线位置，误差在千分之几 |
| 手指在两次事件之间 | 位置不变 | 游戏也是这么读的（每帧读当前触点）；所以横向偏差逐帧漂 |
| 判定线几何 | 分段线性插值（与游戏一致） | `UpdateInfo` 只写位置与角度，插值在事件之间是线性的 |
